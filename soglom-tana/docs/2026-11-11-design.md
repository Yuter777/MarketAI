# Sog'lom Tana — design spec

Date: 2026-11-11 · Status: awaiting approval · Companion: [implementation plan](./2026-11-11-implementation-plan.md)

## 1. What we are building

A mobile-first PWA that helps adults in Uzbekistan lose fat in a healthy way:
calorie and macro tracking, AI food recognition (text and photo), workouts,
progress tracking and an AI coach. Uzbek (Latin) is the default language,
Russian the second. It must be safe for many users from day one: RLS on every
table, no secrets in the browser, per-user AI limits, and logged AI cost.

**Governing rule: math in code, language in AI.** Every health number is
computed by tested TypeScript. Gemini only reads food text and photos, estimates
portions, and writes friendly text. Every AI nutrition estimate is an editable
draft the user confirms before it is saved.

Success means: a new user can sign up, finish onboarding, log a meal by search,
text or photo, and see the dashboard update — on a phone, in Uzbek, with the
calorie target never going below the safety floors.

## 4. Architecture

```
Browser (PWA)
  ├─ Server Components ── read via Supabase server client (user JWT, RLS applies)
  ├─ Server Actions ───── all mutations: Zod parse → Supabase (RLS) → revalidate
  └─ Route Handlers ───── /api/ai/* (text, photo, coach stream, suggestions, weekly)
                            guard: auth → kill-switch → rate limit → cache → Gemini
                            /api/export, /api/push/*, /api/cron/*
lib/health   pure functions, no I/O            (unit tested)
lib/ai       Gemini wrapper, prompts, schemas  (server-only)
lib/db       typed Supabase clients + queries  (server-only except browser client)
```

- **Server Components by default.** Client components only for forms, the
  dashboard's optimistic lists, charts, camera, chat and timers.
- **Reads:** the page's Server Component fetches the initial data and passes it
  to TanStack Query as initial data. **Writes:** Server Actions, with optimistic
  updates for food and water.
- **Service-role key** is used in exactly four places, all server-only modules
  guarded by `import "server-only"`: AI logging/cache, rate-limit fallback,
  account deletion, admin statistics.
- **Session refresh and CSP** run in `proxy.ts` (Next 16's middleware): refresh
  the Supabase cookie, set a nonce-based Content-Security-Policy, redirect
  unauthenticated users away from `(app)` routes.
- **The user's day.** Every log row stores `log_date date`, computed from
  `profiles.timezone` (default `Asia/Tashkent`). No UTC-midnight bugs.

## 5. Health engine (`lib/health`)

Pure functions, no I/O, fully unit-tested.

| Function | Rule |
|---|---|
| `bmr` | Mifflin–St Jeor: `10w + 6.25h − 5a + 5` (male), `− 161` (female) |
| `tdee` | BMR × 1.2 / 1.375 / 1.55 / 1.725 / 1.9 |
| `bmi`, `bmiCategory` | WHO categories |
| `calorieTarget` | Lose: deficit 15% (slow) or 20% (normal). Then clamps, in this order: deficit ≤ 25%; weekly loss ≤ 1% of body weight (7700 kcal per kg); floor 1500 kcal (men) / 1200 kcal (women). Maintain: TDEE. Gain: +5% (slow) / +10% (normal). |
| BMI < 18.5 | Never a deficit. Returns a maintenance plan plus a `seeDoctor` flag. A goal weight that would mean BMI < 18.5 is rejected with a kind explanation. |
| `macros` | Protein 1.8 g per kg of reference weight (clamped to 1.6–2.0). Reference weight = current weight, or for BMI ≥ 30 the adjusted weight `w25 + 0.25 × (current − w25)`, where `w25` is the weight at BMI 25. Fat 28% of kcal. Carbs = the remainder. |
| `exerciseKcal` | `MET × kg × hours`, MET table in code |
| `stepsKcal` | distance = steps × 0.415 × height; kcal ≈ 0.5 × kg × km |
| `timeline` | Weeks to goal from the clamped weekly rate, shown as a range |
| `ageGate` | Under 18: no plan is created |
| `shouldRecalculate` | True when weight differs by ≥ 2 kg from the weight stored on the active `goals` row |
| `rateFood` | 🟢 / 🟡 / 🔴 from calorie density, protein per 100 kcal, sugar, fat, fiber, processing level; returns a reason key and a swap key |

Every function returns the result plus a list of `adjustments` (for example
`FLOOR_APPLIED`, `RATE_CAPPED`), so the UI can explain kindly why a more
aggressive plan was not allowed.

## 6. Database

Migrations in `supabase/migrations`. All tables have RLS enabled.

**User data** (policy: `user_id = (select auth.uid())` for all operations; index on `(user_id, log_date)` for logs)

| Table | Key columns |
|---|---|
| `profiles` | id = auth user id, sex, birth_date, height_cm, activity_level, goal, pace, dietary_notes, locale, timezone, units, onboarded_at |
| `goals` | versioned targets: weight_kg at calculation, goal_weight_kg, bmr, tdee, kcal_target, protein_g, fat_g, carbs_g, adjustments, valid_from, valid_to |
| `weight_logs`, `body_measurements` | log_date, weight_kg / waist, chest, hips, arm |
| `progress_photos` | storage_path, taken_on |
| `food_logs` | log_date, meal_type, food_id (nullable), **name, grams, kcal, protein, fat, carbs snapshot**, source (`catalog` / `ai_text` / `ai_photo` / `manual`), ai_confidence, photo_path |
| `food_favorites` | food_id |
| `recipes`, `recipe_items` | owner's recipes, ingredients by food and grams |
| `water_logs`, `step_logs` | log_date, ml / steps, source |
| `workout_sessions`, `workout_sets` | plan item, exercise, reps, weight_kg, duration_s, kcal |
| `user_plans` | which ready plan the user follows, current week |
| `chat_threads`, `chat_messages` | role, content, summary of trimmed history |
| `push_subscriptions`, `reminder_settings` | Web Push endpoint, reminder times |

**Catalog** (readable by any signed-in user; writable only by admins)

| Table | Key columns |
|---|---|
| `foods` | owner_id (null = catalog; set = the user's custom food, visible only to them), name_uz, name_ru, aliases[], per-100 g kcal/protein/fat/carbs/sugar/fiber, category, processing_level, is_fried, is_sweet_drink, source (`estimate` / `verified` / `user`) |
| `food_portions` | food_id, label_uz, label_ru, grams |
| `exercises` | names, MET, muscle groups, difficulty, equipment, instructions uz/ru |
| `workout_plans`, `workout_plan_items` | ready plans, day, sets × reps, weekly progression rule |

**System** (no client access at all; written with the service role)

| Table | Key columns |
|---|---|
| `ai_requests` | user_id, feature, model, prompt_version, tokens_in, tokens_out, cost_estimate, latency_ms, status. Admins can read. |
| `ai_cache` | key = sha256(feature + prompt version + model + locale + normalized input), result jsonb, expires_at |
| `rate_limit_counters` | user_id, feature, day, count — the fallback when Upstash is not configured |
| `app_admins` | user_id |

Other points:

- **Admin role** lives in `app_admins`, checked by a `security definer` function
  `is_admin()`. It is not a column on `profiles`, because users can update their
  own profile row.
- **Food search:** `pg_trgm` GIN index over `name_uz`, `name_ru` and aliases,
  queried through an RPC that ranks by similarity.
- **Storage:** private buckets `food-photos` and `progress-photos`, object path
  `{user_id}/…`, policies restricted to the owner's folder, read through
  short-lived signed URLs only.
- **Deletion:** every user table has `on delete cascade` to `auth.users`.
  Deleting an account removes storage objects, then the auth user.
- **Types:** `lib/db/database.types.ts` generated from the schema.

## 7. AI layer (`lib/ai`)

One wrapper, `generateStructured({ feature, userId, schema, system, contents })`:

1. Kill-switch (`AI_DISABLED=true`) → typed `AI_UNAVAILABLE` result.
2. Per-user daily limit (photo 15, text 60, coach 40; each overridable by env).
3. Cache lookup for text features.
4. Gemini call with the JSON schema derived from the Zod schema, a 20 s
   timeout, and 2 retries with exponential backoff on 429 and 5xx.
5. Zod validation, then numeric sanity clamps (for example 0–900 kcal per
   100 g, 1–2000 g per item).
6. Row in `ai_requests` with tokens, cost estimate, latency and status.

Callers always receive a discriminated result (`ok` / `rate_limited` /
`unavailable` / `invalid`). Any non-`ok` result opens manual entry with a
friendly message. Nothing throws to the UI.

| Function | Notes |
|---|---|
| `parseFoodText` | Text → items (name, quantity, unit, grams, kcal, P/F/C, confidence). Each item is matched against the catalog by trigram similarity; on a match the catalog's values replace the AI's. Cached. |
| `recognizeFoodPhoto` | The client compresses to ≤ 1024 px WebP/JPEG. The server checks MIME type, magic bytes and size (≤ 2 MB). Same item schema and catalog matching. |
| `mealSuggestions` | Rules choose 3 catalog meals that fit the remaining kcal and macros. AI only writes the friendly sentence, with a plain template fallback. |
| `weeklySummary` | Numbers computed in code. AI writes one encouragement and one tip. |
| `coachReply` | Streamed. Context = profile, targets, 7-day summary, a rolling summary of older messages, and the last 12 messages. |

**Prompts** live in `lib/ai/prompts.ts`, each with a version string and Uzbek
few-shot examples ("2 ta somsa", "yarim kosa osh", "bir burda non").

**Prompt injection.** User text and image content are passed as delimited data.
The system instruction states that content inside them is never an instruction.
The model has no tools. Output is schema-constrained and clamped, so the worst
case is a wrong draft that the user can see and edit.

**Coach guardrails**, in two layers:

- *Prompt:* answer in the user's language, short and practical; evidence-based;
  no extreme diets, fasting challenges, detox, fat-burner pills, steroids, SARMs
  or hormones; never diagnose; send symptoms to a doctor; never go below the
  calorie floors.
- *Code (`lib/ai/safety.ts`):* a deterministic screen for disordered-eating
  signals in Uzbek and Russian runs before the model. On a match the coach
  switches to care mode: no numbers, a caring reply, encouragement to seek
  professional help. A second screen flags medical symptoms. The reply is also
  checked for calorie figures below the user's floor.

The UI shows "Bu tibbiy maslahat emas." under the chat.

## 8. Features

- **Onboarding:** 5 short steps → summary screen (BMI and category, kcal
  target, macros, timeline range, plain-language explanation). Under 18: a
  friendly message recommending a doctor or parent, and no plan.
- **Dashboard:** calorie ring, macro bars, water, steps, exercise burned, and
  meals grouped as Nonushta / Tushlik / Kechki ovqat / Gazak.
- **Add food:** search, free text, photo; plus favorites, recents, "repeat
  yesterday's breakfast", custom foods and recipes.
- **Food catalog seed:** about 150 items with uz and ru names, aliases,
  per-100 g values and typical portions. Halal only: no pork, no alcohol. Every
  row is `source: 'estimate'`. I author the values from general nutrition
  knowledge; they need verification before you treat them as authoritative.
- **Recommendations:** 🟢 Tavsiya etiladi / 🟡 Me'yorida / 🔴 Kamroq iste'mol
  qiling, with a one-line reason and a swap. Never "forbidden", never shaming.
- **Workouts:** exercise catalog, three ready plans, progressive overload
  suggestions, set and cardio logging, rest timer, history, streaks, manual
  steps behind a `StepSource` interface for Google Fit / Apple Health later.
- **Progress:** weight chart with 7-day moving average, measurements, private
  photos, weekly summary.
- **Coach:** streamed chat with persistent history.
- **Settings:** language, units, theme, recalculate plan, reminders, export
  (JSON and CSV), delete account.
- **Admin:** food catalog management, AI usage and cost per day, users and DAU.

## 9. Security

- Secrets only in server modules marked `server-only`. A unit test fails the
  build if `GEMINI_API_KEY` or `SUPABASE_SERVICE_ROLE_KEY` is referenced from a
  client module.
- Nonce-based CSP, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`.
- Zod on every Server Action and Route Handler; body size limits; text input
  ≤ 500 characters; images ≤ 2 MB with MIME and magic-byte checks.
- RLS tests in SQL: user A cannot read or write user B's rows in any table, and
  a non-admin cannot write the catalog.
- Cron and push routes require a shared secret header.

## 12. Choices where I picked the simpler or safer option

Tell me if you want any of these changed.

1. **No locale prefix in URLs.** The language comes from the profile and a
   cookie, not `/uz/...`. Simpler for an installed app. The landing page is
   therefore not separately indexable per language.
2. **Reminders use Web Push**, triggered hourly by Supabase `pg_cron` calling a
   protected route. A PWA cannot reliably schedule local notifications while
   closed. This needs no paid service. iOS only delivers push to an installed
   PWA.
3. **Food photos are stored** in the private bucket, linked to the log entry
   and deletable by the user. The alternative is to analyse and discard.
4. **Under-18 users** may keep an account but get no plan and no health data is
   stored for them.
5. **Gain-muscle goal** uses a +5% / +10% surplus. The brief does not specify one.
6. **Sentry and Upstash** are used on their free tiers and are optional. I will
   not add any other external service without asking.
7. **Telegram login later:** nothing in the schema depends on email. Profiles
   key on the auth user id, so Telegram can be added as another identity.
